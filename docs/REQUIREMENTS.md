# Sherpa — требования (черновик v0.1)

## 1. Назначение

Sherpa — система для удобной настройки и обслуживания парка серверов.
С серверами Sherpa работает только по SSH, агенты на серверах не ставятся.

## 2. Платформы

| Платформа | Формат поставки | Очередь |
|-----------|-----------------|---------|
| Linux     | `.deb`, AppImage | сейчас |
| Windows   | `.exe` (установщик) | сейчас |
| Web       | веб-приложение | сейчас |
| macOS     | — | позже |

## 3. Архитектура: ядро + фронты

### 3.1 Ядро (Core)
- Одно компилируемое ядро, **одинаковое на всех платформах**: одна кодовая база
  и один набор функций. Если функция есть в ядре, она есть везде.
  Ситуация «на Windows это ещё не выпустили» исключена архитектурно.
- Ядро принимает запросы (по аналогии с системными вызовами) и возвращает ответы.
  Вся бизнес-логика живёт в ядре: SSH, сервера, команды, файлы и т. д.
- Протокол запросов и ответов один, версионированный, независимый от фронта.

### 3.2 Фронты
- Фронт — только интерфейс. Он отправляет запросы ядру и показывает ответы.
- На разных платформах фронты разные, бизнес-логики в них нет.
- Добавление новой функции = новый вызов в ядре + отображение во фронтах.

### 3.3 Принятые решения
- **Язык ядра:** Rust.
- **Десктоп-фронты:** нативные для каждой ОС.
- **Ядро — CLI-программа** `sherpa-core <команда> [аргументы]`, ответ в JSON
  в stdout, сетевого API нет. Долгие операции (терминал) работают в
  долгоживущем процессе, обмен потоком через stdin/stdout (JSON Lines).
- **Варианты поставки:**
  - **Десктоп (Linux, Windows):** нативное приложение, которое вызывает локальный
    `sherpa-core`.
  - **Web = self-hosted:** на сервере стоят `sherpa-core` и сайт на Laravel.
    Laravel служит фронтом и вызывает `sherpa-core` на том же сервере.
- **Состояние ядра:** у ядра своя БД (SQLite). В ней между запусками хранятся
  подключения, группы, теги, статусы, host keys и т. п. Каждый вызов CLI читает
  и пишет её.
- **Длинные сессии (терминал):** реализуются силами ядра; механизм уточним на
  этапе проектирования.

## 4. Первая версия (MVP): «Подключения»

### 4.1 Подключение (карточка сервера)
- Поля: имя, хост, порт (по умолчанию 22), пользователь, способ входа,
  описание, группа, теги.
- Операции: создать, просмотреть, изменить, удалить, дублировать.

### 4.2 Способы входа
- Пароль.
- SSH-ключ: путь к файлу или ключ, вставленный текстом (с парольной фразой
  или без).
- Не входят в MVP: ssh-agent, jump host / bastion.

### 4.2.1 Терминал
- Открыть интерактивную SSH-сессию (PTY) к подключению прямо в приложении.

### 4.3 Проверка и статус
- «Проверить подключение»: соединение, авторизация, понятный текст ошибки
  (хост недоступен, неверный пароль/ключ, таймаут и т. п.).
- Статус сервера в списке: онлайн / офлайн / ошибка авторизации / не проверялся,
  время последней проверки.
- Host key: отпечаток показывается и сохраняется при первом подключении,
  при смене ключа выводится предупреждение (TOFU).

### 4.4 Группы, теги, импорт
- Группы (папки) для подключений, теги, поиск и фильтр по имени, хосту и тегам.
- Импорт из `~/.ssh/config` (Host, HostName, Port, User, IdentityFile).

### 4.5 Хранение
- Подключения и секреты (пароли, ключи, парольные фразы) лежат в зашифрованном
  хранилище у ядра.
- Секретные поля в БД ядра шифруются (AEAD) **ключом из ключ-файла**. Схема одна
  на всех платформах.
  - Ключ-файл генерирует ядро при первом запуске (случайный ключ 256 бит).
    Он лежит отдельно от БД, права 600, путь задаётся в конфиге ядра.
  - Мастер-пароль не используется: его могут забыть.
  - Self-hosted: у Laravel нет доступа к ключ-файлу.
  - Без ключ-файла секреты не восстановить. Ядро даёт команду экспорта
    ключ-файла для резервной копии, а фронт при первом запуске предлагает
    сохранить копию.
- Секреты не отдаются фронту без необходимости и не пишутся в логи.

### 4.6 Пользователи и роли (Web)
- Серверным ядром пользуется команда: несколько учётных записей, вход по логину
  и паролю.
- Роли и права — позже, не в MVP.
- Десктоп: один локальный пользователь, без ролей.
